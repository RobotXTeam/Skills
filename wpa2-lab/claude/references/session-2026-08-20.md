# Lab Session Log — 2026-08-20

Full record of the first WPA2 penetration learning session. Documents what was attempted, what worked, what failed, and the two "cheats" identified that motivated the honest-mode plan.

## Setup

- **Target AP**: seeed @ 192.168.2.113, Ubuntu 22.04, RTL8822CE wlp4s0.
- **Attack box**: steven (local), Ubuntu, Intel wlp0s20f3 (iwlwifi).
- **AP config**: hostapd WPA2-PSK/CCMP, SSID `LAB-WPA2-TEST`, channel 6, BSSID `a8:93:4a:0b:51:27`.
- **First password**: `XqFDQKQb` (8-char, mixed into the test dictionary).

## What worked

1. **Honeypot AP** stood up cleanly on seeed with hostapd + dnsmasq. `nmcli dev set wlp4s0 managed no`, manual IP assignment, hostapd `-B` backgrounded. AP-ENABLED, channel 6, WPA2 CCMP confirmed.
2. **RTL8822CE capability check** via `iw phy phy0 info`: confirmed AP and monitor both supported as interface modes.
3. **Phone client connected** to `LAB-WPA2-TEST` with password `XqFDQKQb`. hostapd logged full 4-way handshake (AP-STA-CONNECTED, EAPOL-4WAY-HS-COMPLETED), got IP 192.168.7.34 via dnsmasq.
4. **hostapd `-dd -K` debug dump** captured the entire handshake material: ANonce, SNonce, PMK, PTK, KCK, KEK, TK, the full 121-byte 2/4 EAPOL frame with MIC. This validated the algorithm inputs.
5. **PMK derivation verified**: `wpa_passphrase "LAB-WPA2-TEST" "XqFDQKQb"` produces `9f0b6020...` — exactly matches the PMK in hostapd's internal log. PBKDF2-HMAC-SHA1 implementation confirmed correct.
6. **sha1_prf implementation verified** against hostapd's standard test vector (key0=20×0x0b, label="prefix", data="Hi There") — exact match.
7. **Hand-constructed pcap** from the raw EAPOL hex: after fixing the 802.11 frame header (FC byte order, ToDS/FromDS address assignment, correct MIC field offset, correct pcap linktype=105), aircrack-ng recognized it as `WPA (1 handshake)`.
8. **Dictionary crack succeeded**: `aircrack-ng -w wordlist.txt -e LAB-WPA2-TEST -b A8:93:4A:0B:51:27 handshake.pcap` → `KEY FOUND! [ XqFDQKQb ]` at 2185 k/s, 56th candidate. Full PMK/PTK/MIC chain printed and matched.

## What failed

1. **Single-card AP+monitor on RTL8822CE**: adding `mon0` monitor interface on phy0 flipped `wlp4s0` from AP to monitor, breaking hostapd. rtw88 driver does not support simultaneous AP + monitor on one phy.
2. **steven Intel monitor capture**: airodump-ng on wlp0s20f3 captured 6411 then 11938 frames but **0 EAPOL**. Intel iwlwifi monitor mode on this chipset misses EAPOL data frames. aircrack reported `WPA (0 handshake)` even after aireplay-ng deauth bursts and a confirmed client reconnect.
3. **aireplay-ng deauth from steven**: deauth frames transmitted (5× broadcast DeAuth code 7), client was kicked, reconnect happened, but capture still showed 0 EAPOL. The deauth worked; the capture didn't.
4. **Hand-rolled PTK derivation in Python**: PMK correct (verified via wpa_passphrase), sha1_prf correct (verified via test vector), but the PTK computed from the real PMK + real AA/SA/ANonce/SNonce did NOT match the PTK in hostapd's log. Tried: min/max sorted, raw order, different addr/nonce pairings, SHA1 vs SHA256, single-block vs multi-block counter, KDF-SHA256 with 16-bit big-endian counter. None matched. Root cause not determined. **However, aircrack-ng cracked the same handshake successfully**, so the algorithm is correct in aircrack; the Python reimplementation has a subtle bug. The Python script is kept as teaching reference for the algorithm shape, but production cracking should use aircrack-ng/hashcat.

## The two "cheats" (honesty audit)

This session was NOT a true attacker-perspective test because of two shortcuts:

1. **Cheat #1 — handshake data from AP internals**: the 2/4 frame hex, ANonce, SNonce, and MIC all came from `hostapd -dd -K` debug log on the AP itself. A real attacker only gets over-the-air frames via monitor capture. steven's Intel card failed to capture them, so we fell back to the AP's internal log. This is data the attacker cannot access.
2. **Cheat #2 — password in dictionary**: the test password `XqFDQKQb` was explicitly inserted into the wordlist to guarantee a successful crack for toolchain validation. A real attacker does not know the password and the dictionary would not coincidentally contain a random 8-char string.

## Honest-mode plan (next session)

To run a true attacker-perspective test:

1. **Password lives only on the AP** in `hostapd.conf`. Never written to any attack-box file. The attack box genuinely does not know it.
2. **No `-dd -K`** on hostapd. No internal PMK/PTK dump. AP logs only basic association events.
3. **Capture via a card that actually gets EAPOL**: Raspberry Pi 4/5 built-in (Cypress) for passive, OR a RTL8812AU/AR9271 USB card for active deauth. Do NOT use steven's Intel card for capture.
4. **Dictionary does not contain the answer**. Use mask attack (`?d?d?d?d?d?d?d?d` for 8-digit, etc.) or a real weak-password list (rockyou) without seeding the target.
5. **Trigger handshake** either by asking the user to manually reconnect the phone (passive mode, no injection needed) or by running aireplay-ng deauth from an injection-capable card.
6. **Accept honest failure**: if the dictionary/mask does not cover the password, the crack simply does not succeed. That is a valid outcome demonstrating password strength.

## Key takeaways (what to remember)

1. WPA2 cracking is offline. The hard part is capturing one handshake; the crack itself is pure computation.
2. The handshake is a transient connection event. No client reconnect = no handshake = no crack. deauth exists to manufacture this event.
3. Monitor-mode capture quality varies wildly by chipset/driver. Intel consumer chips are unreliable for EAPOL. Cypress (Pi) and Realtek USB adapters are reliable.
4. Injection support is rare and chipset-specific. Pi built-in and Intel don't support it. RTL8812AU/AR9271 do.
5. Password length is the dominant security factor. 8-char is GPU-crackable in minutes-to-hours; 12+ char random is effectively uncrackable.
6. Auto-connect phones are a real risk: an attacker can deauth and force a reconnect to capture a handshake. Turn off auto-connect for untrusted networks.
7. WPA3/SAE defeats this entire attack class by requiring an interactive protocol (no capturable offline-brute-forceable handshake).
