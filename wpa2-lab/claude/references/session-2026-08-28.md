# Session 2026-08-28/29 — Live attack attempt on lab CMCC routers (qiang side)

Goal: user authorized a full demo attack against his own lab WiFi ("CMCC都是我实验室的"), target **CMCC-xbxm** (44:4C:7E:22:E2:01, ch11, WPA2-CCMP, signal ~74). Constraint: never take down the user's own connectivity (Qiang router / this machine's uplink), no sustained disruption. Outcome: **attack chain reached handshake-triggering stage but no crackable hash obtained** — hardware limitation of the only in-range capture card (qiang AX210). User stopped after round 3; everything restored cleanly each time.

## Environment facts established

- Capture host must be local (qiang, 192.168.26.x, Intel AX210 wlp1s0): **seeed's site has zero CMCC visibility** (scan returned empty) — seeed is cracking-host-only for this target; transfer pcaps via scp over Tailscale (`sshpass -p 0 ssh seeed@100.76.45.91`, LAN 192.168.2.113 unreachable from qiang).
- qiang's wlp1s0 is the user's own uplink → capture requires a scripted switch-to-monitor window with guaranteed self-restore (`trap restore EXIT`; restore = `iw set type managed` + `nmcli dev set managed yes` + `nmcli con up Qiang`). Worked flawlessly all 3 rounds.
- Tools installed this session: aircrack-ng + hcxtools on qiang. seeed already has aircrack suite; hcxtools/hashcat were NOT installed there (attack stopped before cracking phase).
- Target AP: beacon RSN caps 0x000c → **no PMF** (MFPC/MFPR=0) → deauth viable. Two associated clients at start: E6:83:CE:D6:80:3D, 1A:8B:E5:A1:1B:76 (locally-administered/randomized MACs — they rotate between sessions).
- User's phone had NO saved password for the target → trigger = deauth (owner-authorized), not manual reconnect.

## Round 1 (23:48–23:53) — injection WORKED, M1/M2 lost

Script: switch to monitor ch11 → airodump-ng capture → `aireplay-ng -9` prime → 14 cycles of `timeout 15 aireplay-ng -0 3 -a BSSID` broadcast deauth.

- Injection verified working: **10355 deauth frames** captured; timing histogram shows exact 768-frame bursts aligned to each cycle start — these are our own TX (SA spoofed to AP). Sender ambiguity check: `aireplay -0` spoofs SA=AP, so distinguish ours vs AP-originated only by timing; all bursts align to our cycles → ours. AP itself does not spontaneously deauth clients (nothing between cycles).
- Client kicks confirmed: full sequence captured at +41 s: ProbeResp → Auth(resp) → ReassocReq → ReassocResp → EAPOL. Second event at +61 s.
- **BUT every handshake arrived incomplete**: round 1 captured M3(+retransmit) of one handshake and M4 of another; M1/M2 missing both times. Missing frames sit in a ~60–70 ms window right after the reassoc burst (auth-req of the same burst was also missing). aircrack `0 handshake`; hcxpcapngtool extracted nothing (PMKID only exists in M1 — absent).
- Side lesson: airodump's ANSI screen output appended to a log file grew **9.3 GB in 5 minutes**. Use `airodump-ng -q` or redirect stdout to /dev/null in scripted runs.

## Round 2 (00:17–00:22) — injection DEAD, zero activity

Changed recipe: tcpdump full capture (with radiotap) + directed deauth `-c CLIENT` per client + broadcast, no `-9` prime first.

- 47536 frames captured, **0 EAPOL** (brute-force LLC 888e scan confirmed), 0 of our injected frames visible, only 7 deauths from unrelated foreign APs. Clients stayed associated the whole window.
- Conclusion: TX injection completely failed this round. The R1→R2 recipe diff (capture engine airodump→tcpdump, prime present→absent, broadcast→directed) — culprit unidentified; iwlwifi injection is simply not trustworthy.

## Round 3 (00:36–00:41) — reverted to R1 recipe; target went invisible

Script: R1 recipe + attempted `iw set monitor flag fcsfail` (NOT supported by iwlwifi).

- Prime reported "Injection is working! Found 2 APs" at 00:36:54, 9 deauth cycles ran.
- **Anomaly**: the resulting pcap contains ~28k frames of which essentially ALL are control frames (BlockAck/ACK); zero beacons, zero data, zero EAPOL from the target; aircrack "No networks found". Either the AP's radio went silent mid-window or the iwlwifi RX path degraded to control-frame-only reception. Unresolved; user stopped the experiment here.

## Parsing/debugging techniques worth keeping

- airodump pcap has NO radiotap (linktype 105); tcpdump writes classic pcap with radiotap (linktype 127) even when named `.pcapng` — check the magic (`d4c3b2a1` = classic pcap). Radiotap skip: `it_len = u16 at offset 2`.
- pcapng EPB layout (if ever needed): block hdr 8 B, then iface_id(4), ts_high(4), ts_low(4), incl_len(4), orig_len(4), data @ +28.
- EAPOL-Key body offsets from EAPOL header byte 0: keyinfo[5:7], replay[9:17], nonce[17:49], MIC[81:97], key_data_len[97:99], key_data[99:]; PMKID = KDE `\xdd\x12\x00\x0f\xac\x04` + 16 B inside M1 key data. M1=ACK only; M2=MIC+kdl>0; M3=ACK+MIC+Install; M4=MIC+kdl==0.
- Beacon PMF check: RSN IE (tag 0x30) last 2 bytes = capabilities; bit6=MFPC, bit7=MFPR. If either set on the association, deauth is useless — check BEFORE planning an active attack.
- Deauth origin attribution: `aireplay -0` spoofs SA=AP + reason 7, identical to AP-sent frames; use timing correlation with your own cycle starts to attribute.
